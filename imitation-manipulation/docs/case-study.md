# Case study: imitation-manipulation

*A policy learns to push a T-block from human demonstrations — no reward
engineering, no GPU — and you can watch every checkpoint of its training
ladder act live in a browser, then swap the block for a shape it has never
seen and watch what "generalization" actually looks like at this scale.*

## The problem

Imitation learning is the most accessible entry into robot manipulation —
no reward shaping, just demonstrations — but public demos usually show a
polished final policy and hide everything interesting: what the policy
actually sees, how competence grows (and plateaus, and wobbles) across
training, and what happens the moment the world deviates from the training
distribution. The goal here was an honest, laptop-scale demo of exactly
those things, reproducible from a bare clone with no training and no
account.

## Constraints

- **Host:** a GPU-less MacBook (Apple Silicon). Training and native
  inference run on MPS; the demo container is CPU-only (Docker cannot see
  MPS on macOS).
- **Honesty:** every number on screen must trace to a real evaluation of
  the exact checkpoint shown; out-of-distribution runs are labeled as
  probes, never scored as benchmarks; "success" keeps PushT's real ≥95%
  coverage bar even though it means showing 0% everywhere.
- **Self-contained:** a public user runs `docker build && docker run` (or
  `make fetch-artifacts && make demo`) and needs no HF token, no training,
  no Python knowledge.

## The approach

ACT (the smallest, fastest LeRobot policy family) trained on the
`lerobot/pusht` demonstration dataset (206 human episodes), evaluated in
gym-pusht — 2D pymunk physics, pygame rendering, macOS-clean. The demo
tells a **checkpoint-ladder story**: one 5k-step run frozen at 1k/3k/5k
plus a 10k baseline run, each evaluated for real (10 seeded episodes) by
`make eval-ladder`, which generates `outputs/demo/ladder.json` — the single
manifest the UI reads, so every displayed number is machine-traceable to an
`eval_info.json`.

The **generalization probe** is a PushShape env subclass: gym-pusht derives
both its coverage reward and the goal-zone silhouette from the block's
collision shapes, so swapping the T's two rectangles for L/I/Z vertex sets
yields correctly-scored, correctly-rendered variants in ~70 lines, with T
byte-identical to the training env. The policy is pixels-in/actions-out and
only ever saw the T — the L/I/Z runs make "trained ≠ general" visible
instead of claimed.

The app itself is **session-blind by design** (an operator-directed
decision): a plain Gradio app plus an episode runner, streaming every
control step to an embedded Rerun timeline (the 96×96 frame the policy
sees, its actions, the coverage reward). It prints `DEMO READY` when
checkpoints are loaded — the only orchestration surface. Per-user isolation
belongs to whoever runs containers (a website orchestrator spawning one per
visitor, or nobody on a laptop); the app knows nothing about users, so the
local and hosted experience is the same artifact.

Checkpoints are distributed via the public Hub repo
`robium/pusht-act-ladder` (~794 MB: 4 rungs of inference weights, the
manifest, the gallery's eval videos, mirroring the `outputs/` subtree).
`make fetch-artifacts` and the Dockerfile use the identical `hf download`
line.

## Robium components used

The architect skill's manipulation golden path chose LeRobot + gym-pusht;
the environments skill's decision tree kept it uv-native (Docker would cost
MPS) with the container as a demo-only exception. The testing skill shaped
the two-tier bar (`make smoke` = train+eval mechanics; `make demo-smoke` =
the demo ship bar). The lerobot skill's train/eval command templates
carried the pipeline; frictions became learnings
(`learnings/2026-07-12.md`, `2026-07-15-manip-trial.md`,
`2026-08-03-imitation-manipulation.md` in the robium repo).

## Major decisions

1. **Train our own baseline:** no pretrained PushT checkpoint on the Hub
   loads correctly under lerobot 0.6.0 (the official one predates the
   processor-pipeline format; the community migration evals at chance).
   The shipped ladder is reproducible from this repo's own targets.
2. **Manifest generated by evaluation, never hand-edited:** the UI can only
   show numbers that came out of a real eval run — honesty by construction
   rather than by review.
3. **Session-blind app; isolation at the container boundary:** deleted the
   per-app FastAPI session gateway (claims/409/403/timers). One process
   serves one demo; `DEMO READY` is the whole contract. (This retired the
   old robium-website page's gateway integration — flagged, not hidden.)
4. **Shape variants as probes, not benchmarks:** OOD runs are labeled
   "out-of-distribution probe — the policy only ever saw the T"; the
   metrics table stays T-only because that is what the evals measured.
5. **CPU torch wheels in the demo image:** the default linux torch wheel
   drags a multi-GB CUDA dependency train a CPU container never uses — it
   turned the image build into a 40-minute download that kept getting
   killed. Installing `torch`/`torchvision` from the PyTorch CPU index
   first cut the layer to ~1 minute.

## Results

- `make smoke`: 200-step train + 2-episode seeded eval, green in ~40 s warm
  on an M2 Pro (2026-08-05).
- `make demo-smoke`: app boots to `DEMO READY`; a T episode and an
  out-of-distribution L episode complete through the Gradio API; 3 tests
  green in ~35 s natively and against the container.
- Ladder (10-episode seeded evals, 2026-08-03 artifacts):
  `avg_max_reward` 1k 0.182 · 3k 0.239 · 5k 0.322 · 10k 0.310;
  `pc_success` 0% at every rung. The ladder is honestly non-monotonic — the
  5k rung out-evals the 10k baseline — and the demo defaults to the
  strongest *measured* rung (5k), not the longest-trained.
- The self-contained image builds from a bare clone (artifacts fetched from
  the Hub at build time, boot probe at build time) and serves the identical
  app the native path runs.

## Limitations

- PushT is a 2D toy task; nothing here claims real-robot transfer.
- ACT at 5–10k steps never reaches PushT's ≥95%-coverage success bar —
  `pc_success` 0% is the expected, displayed reality; max-coverage reward
  is the honest metric.
- 10-episode seeded evals are noisy; the non-monotonic ladder ordering is
  a real measurement, not a stable ranking claim.
- OOD shape runs are qualitative probes; no OOD metric table is published
  on purpose.
- The hosted robium.ai page for this app is retired pending a website-side
  update to container-level sessions (`robium-app.yaml` sets
  `demo.hosted: false` and keeps the forward orchestrator config).

## Next steps

Promotion to the public robium-apps showcase; re-enabling the hosted demo
once the website island supports plain HTTP apps with container-level
sessions; and using this app as the bootstrap base
(`robium-ai app new <id> --from imitation-manipulation`) for the next
LeRobot-class train/eval/demo application.
